## 定位与实现

独立运行真实目录界面的 7 项测试，再刻意交由后台线程进行垃圾回收，复现 5 条 `Variable.__del__ / main thread is not in main loop`。记录中的创建位置均指向目录配置的普通字段；这说明异常可以来自先前关闭的表单，不能仅凭日志位置归因于随后运行的制作策略线程。

管理器各模块改用明确绑定所属控件的变量。作用域持有变量，在所属控件销毁时由界面线程先移除实际 Tcl trace/回调命令，再销毁 Tcl 变量，最后释放变量对解释器和根窗口的引用。关闭子控件不提前清理其父控件变量；不同 Tk 根窗口使用各自解释器。保留关闭后的 Python 变量或引用循环，不会再次触发跨线程 Tcl 变量清理。没有全局替换 Tkinter、吞掉析构异常或在产品里关闭垃圾回收。

诊断还暴露出另一个问题：旧控件引用循环若最后在后台被回收，可能导致 Tcl 解释器自身被错误线程释放。CPython/Tk 运行时为已登记解释器保留一个引用；后续界面操作检查到没有其他对象持有它时，再由界面线程释放。正常进程退出也在主线程释放所保留的引用。独立子进程反复创建/销毁窗口、后台回收、界面释放三轮，验证没有 Tcl 线程崩溃，且登记表清空。该机制针对当前 CPython/Tk 管理器运行时，不宣称其他 Python 实现已验收。

目录读取和素材服务操作改用共享后台调用器：后台仅接收服务函数、普通参数与结果队列；界面完成/错误回调留在界面线程。关闭窗口撤销定时轮询并解除界面回调，已开始的本地操作完成一次。目录查询不改配置，关闭面板不停止独立素材服务，也不代表取消远端视频任务。视频导入和本地 GIF 窗口也补齐销毁时取消轮询。

部分旧创作表单仍保留各自后台包装器，尚未全部迁入共享调用器；此次变量清理覆盖管理器模块，不能据此声称所有旧后台闭包都已清除。配置、凭据、任务恢复协议和媒体审核规则不因窗口清理而放宽。
