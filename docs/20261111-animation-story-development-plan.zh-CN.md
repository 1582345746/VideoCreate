# 动画故事创作模块：参考研究与开发清单

日期：2026-11-11。本文保留开发规划与前期研究依据；首版实现与测试结果另见 [开发验收记录](20261111-animation-story-acceptance.zh-CN.md)。前期研究未调用付费模型；实现阶段另有真实请求记录，不应混为一轮。

## 1. 已确认的产品定位

用户提供真人短视频，主要是提供剧情参考。系统理解其中的事件、人物关系、情绪变化、笑点或感动点，再重新创作动画剧本、角色、场景、美术、镜头和声音。

成片中的场景重新设计和生成。原片的真人外貌、地点、服装、构图、镜头数、时长和背景音乐都不自动成为成片要求。源视频时间点用于说明剧情依据，不强制输出镜头逐帧、逐秒对应。

上层建立通用的“动画故事创作”模块。“噜噜与噜妹”是第一个主题子模块，之后可以配置其他双主角、动物组合、原创人物、不同世界和美术风格。生成、路由、账本、剪辑和验收继续共用 VideoCreate 底座。

核心创作链：

> 参考剧情 → 提炼事件与情绪 → 明确保留的故事要点 → 选择动画主题与角色 → 重新设计世界和场景 → 编写动画剧本与分镜 → 生成关键帧 → 分镜视频 → 配音剪辑 → 验收交付。

## 3. 应沉淀的创作规则

### 3.1 剧情保留什么

提炼“谁想做什么—遇到什么—如何选择—引起谁的反应—最后发生什么”。喜剧另记铺垫、误解、揭示、反差和回扣；温情故事另记关心、犹豫、接纳和情绪落点。

每个参考记录两类内容：

- 必须保留的故事要点：例如一句话改变另一人的态度，或某次接触直接造成后面的反应。
- 可自由创作的内容：角色外观、场景地点、时代、色彩、服装、镜头、对白措辞，以及不影响事件逻辑的道具。

具体哪类内容属于必须保留，要看原故事的作用。若笑点就是“用脚堵住嘴”，不能改成毫不相关的温柔拥抱；如果题眼是“口是心非”，场景和讨好方式可以重新设计。重写后的差异要有创作说明。

### 3.2 角色固定什么、允许变什么

用户后来补充的两张人物三视图明确了角色身份：水豚噜噜与噜妹，黄色圆脸、短肢、橙色圆钝大鼻吻部与细小嘴、小圆耳和橘子绿叶头饰。噜噜默认橙色短裤；噜妹默认白色荷叶边睡帽、帽顶托盘橘子和粉色睡衣。早期把口鼻描述成“宽嘴”的推断造成鸭嘴生成，属于身份设计错误；以用户人物图纠正，不能把鸭子候选当作身份依据。服装、头饰和渲染变体另行版本化。

角色包区分身份特征、表情、姿态、服装和饰品。更衣可以是正常创作；同一段连续场景中无解释地变脸或变装是缺陷。不要把单片中的“大哥哥/小妹妹”比例、亲属关系或衣服推广到全部故事。

其他主题可使用完全不同角色。每条故事把抽象角色功能，如“主动讨好的一方”“表面生气的一方”，分配给所选角色；不以真人外貌、性别或站位自动决定映射。

### 3.3 世界与美术独立创作

场景设计从新故事的行为需要出发：是否需要容纳两人并排、是否有能接触的道具、是否需要藏住信息再揭示、角色短手短脚是否够得到物品。统一角色与环境的材质、比例、光线和景深。

原片可以发生在卧室，动画可以重写到云上小屋、温暖客厅或其他新世界，只要新的场景让同一情绪和因果成立。声音、对白和背景音乐也按新版本重新设计。

因此需要开发创作层和素材管理层，现有生成、路由、账本、时间线和审核底座继续使用。

## 5. 建议模块结构

```text
VideoCreate
├─ 动画故事创作 animation
│  ├─ 参考剧情理解：事件、人物功能、情绪、题眼
│  ├─ 故事改编：保留要点、新剧本、新对白
│  ├─ 角色与世界设计：角色包、场景包、美术方案
│  ├─ 导演设计：构图、表演、道具接触、声音、分镜
│  └─ 主题子模块
│     ├─ 噜噜与噜妹
│     ├─ 其他固定双主角
│     └─ 其他原创动漫人物与故事
└─ 共用制作底座
   ├─ 独立生图模型与上游
   ├─ Muse / Grok / Seedance 等视频模型与上游
   ├─ 配音与音效
   ├─ 任务恢复与预算
   └─ 本地剪辑与内容审核
```

实现建议：通用逻辑放在 `src/videocreate/animation/`；噜噜主题放在版本化主题包中。主题包组合角色、可选场景、美术和表演规则，不复制一套支付、下载或剪辑代码。首版先完成噜噜主题的实际使用链路，再用第二套角色检验通用性。

暂定新入口 `animation`；自然语言请求会选择对应主题。下面的命令名称仅为设计示意，尚未实现，也未在本轮执行：

- `animation inspect`：导入参考，形成剧情研究。
- `animation adapt`：选择主题并编写新剧本与场景设计。
- `animation plan`：生成可验证的 v3 制作计划。
- `animation run`：调用现有 assets/jobs/timeline，先小样再扩展。
- `animation review`：检查剧情要点、主题一致性和实际成片。

## 6. 完整开发清单

优先级说明：P0 是形成可用制作闭环的必要项；P1 是稳定重复制作的必要优化；P2 是验证首版后扩展的能力。实际完成以产物与验收为准。

| 编号 | 优先级 | 开发项 | 具体交付与验收 |
| --- | --- | --- | --- |
| A01 | P0 | 产品契约与数据设计 | 定义 animation 项目、主题、参考剧情、角色、场景、剧本和设计版本。原片剧情约束与画面设计约束分开；新增字段有 Schema 与迁移规则，老项目可正常读取。 |
| A02 | P0 | 批量参考管理 | 接收本地视频，记录 SHA-256、媒体规格、来源和角色/剧情/美术等参考用途；支持中文、空格、#、emoji 文件名；重复素材可识别。当前 12 片成为首批回归样本。 |
| A03 | P0 | 剧情理解接口 | 支持连续视频/音频理解或分段分析，并记录能力和时间覆盖。抽帧、OCR、ASR、听音分别记来源和置信度；不把画面字幕当作已听到的对白。缺少音视频能力时输出待核实项。 |
| A04 | P0 | 剧情骨架与保留要点 | 产出人物功能、目标、障碍、选择、结果、情绪曲线、题眼；拆开合集。区分观察、推断、原创，重要判断有源时间点；不擅自发明后续结果。 |
| A05 | P0 | 原创动画改编器 | 根据骨架重新写动画剧本和对白；允许换世界、场景、服装和分镜。逐项说明新故事如何保留题眼及因果；不要求镜头数量和构图照原片。 |
| A06 | P0 | 主题与角色包 | 实现通用角色包和噜噜主题包：身份标识、性格、语气、比例范围、服装变体、单人图、同框图、表情图、参考来源与版本。换装保留身份；独立项目可复用。 |
| A07 | P0 | 原创世界与场景设计 | 生成新世界设定、场景布局、色彩/灯光方案与道具尺寸。核对角色能站、坐、拿、抱、接触；成片场景以新设计为依据。 |
| A08 | P0 | 动画表演与分镜规划 | 把故事拆成“触发—注意—动作/表情—反应—结果”。为短肢、大嘴和大头角色重新安排动作；动作接触有可见目标和结果。镜头数和时长随内容变化。 |
| A09 | P0 | 关键帧生产与筛选 | 从角色包和新场景生成当前镜头的单视图画面；逐镜检查两人身份、人数、衣服、手脚和道具。角色总览/三视图用于设计，视频首帧使用干净单画面。 |
| A10 | P0 | 动画生成编排 | 固定当前任务模型/上游，按依赖运行；先做两个相邻关键镜头。Muse 当前单次上限 10 秒，长片拆镜后本地剪辑；不固定五镜或六秒。保留实际返回参数与模型。 |
| A11 | P0 | 新剧本声音与字幕 | 从改编剧本生成音轨和字幕；记录角色声线、说话/倾听者、台词、停顿与情绪。提供独立音轨入口；原生对白是否适合作为首版路线由小样决定。默认声音设计服务新故事。 |
| A12 | P0 | 成片编辑与内容验收 | 从实际素材选保留区间，检查情绪顺序、笑点揭示、台词完整、接触、角色与场景一致性。分开原参考时间、生成素材时间、最终时间线。导出 MP4、字幕、来源与生成记录。 |
| A13 | P1 | 独立短剧系列模式 | 共享角色/世界版本，每条故事独立场景与初始状态；同时保留承接上一集的连续剧模式。独立故事允许并行准备，不能串入上一条的道具、服装或情绪状态。 |
| A14 | P1 | 固定配音接入 v3 | 评估并接入已有声音工具或配置服务，沉淀噜噜与噜妹各自声线。更换一人的音色只失效其声音与相关后期。大嘴角色口型适配必须实测，不能默认真人口型工具适用。 |
| A15 | P1 | 互动与表情素材库 | 整理反应、困倦、假生气、安慰、喂食、看手机等动作的创作描述、首帧条件与已验收片段。区分接触类与无接触类，复用动作逻辑时保留原故事题眼。 |
| A16 | P1 | 局部修复与缓存 | 生成输入按参考、角色、场景、动作和声音分层版本化。字幕修改只重出字幕，声音修改只重做音轨及必要后期；人物错误只重做相关素材；保留旧候选。 |
| A17 | P1 | 量产记录与成本 | 每片记录请求数、时长、可用素材比例、失败原因、重做原因和已知费用。未知价格单独显示；按真实可用片段比较模型，不按模型名字推测能力。 |
| A18 | P1 | 第二主题通用性验证 | 新建一套不同动漫角色和新场景；同一参考剧情能产出另一版故事计划，不复制底层执行代码，不要求出现噜噜元素。主题包可独立升级。 |
| A19 | P2 | 更多动画美术与题材 | 按实测增加不同 3D、二维卡通、古装、冒险及更多配角。每种美术单独建立一致性标准；不能只替换 style 字段就宣称质量相同。 |
| A20 | P2 | 可选视频参考/动作控制 | 仅在确切上游支持并验证输入合同后接入。当前需求以剧情参考和重新创作为主，此项不作为首版前提。精确动作控制单独评估成本和必要性。 |

## 7. 关键实现决策

### 7.1 剧情理解和视频生成分开配置

剧情理解模块负责理解参考片；Muse/Grok/Seedance 等生成模块负责执行新分镜。没有证据表明当前 Muse API 本身能理解整段真人参考并自动完成新故事。首版不把“能生成视频”当作“能解析视频”。音视频理解服务应有独立适配器或人工观察输入，避免把原 MP4 发到不支持它的接口。

### 7.2 角色包、世界包、美术包分别管理

噜噜角色可以出现在居家、雪地、神话或其他世界；同一世界也可以用其他人物。稳定的是已选定版本的角色身份和本片设计约定。首版的包结构服务这条实际工作流，不扩展为复杂素材市场。

### 7.3 接触动作按新角色身体重新设计

写实真人手臂长，水豚角色头大、鼻吻部突出、手脚短。真人的动作描述需要转为可执行的动画动作。若要保留“脚碰到嘴”的题眼，要设计躺坐位置、脚到嘴的距离、支撑和反应，而不是把真人骨架参数直接套上去。

### 7.4 声音设计以新剧本为准

默认从改编剧本规划角色声音和音效，不自动复用原视频声音。原生对白可用于快速小样；长期重复制作要验证固定角色配音。对白、环境声、漫画音效与音乐分别管理；普通字幕由后期生成。固定音色不等于已实现非人脸精确口型，两项分别验收。

### 7.5 首版不重建运行底座

现有同模型上游路由、任务快照、预算、候选、下载、时间线与审核继续复用。已受理任务留在原上游；状态不明的请求不因新主题、换模型或新项目而自动重发。2026-11-10 的 Muse 试镜曾连接超时，这是一条历史记录；本轮没有检查当前服务是否恢复，也没有新增测试请求。

### 7.6 Schema 和产物建议

新增数据均为待开发设计，不能直接把未支持字段塞进当前严格 v3 Schema。建议动画上下文包含以下版本化产物，通过明确入口投射到现有五层计划：

- `source-study.json`：参考用途、剧情观察、时间证据、覆盖范围和待核实项。
- `story-outline.json`：抽象人物功能、事件因果、情绪与题眼。
- `adaptation.json`：保留要点、新剧本、对白及创作差异。
- `animation-context.json`：主题/角色/世界/美术版本与所用资产哈希。
- `design/`：原创角色、场景与分镜设计参考。
- 原有 `brief/story/director/generation-plan/timeline`：继续承担可执行制作计划。

## 8. 开发顺序和实际验收门槛

| 里程碑 | 范围 | 完成标准 |
| --- | --- | --- |
| M1：剧情参考到原创动画计划 | A01–A08 的离线闭环 | 给一段真人剧情，输出有依据的故事骨架、噜噜版新剧本、新场景和可校验分镜；能够解释保留了什么、重新设计了什么。没有媒体生成也能单独验收这一步。 |
| M2：第一条可播放样片 | A09–A12，单条 10–20 秒 | 用已选角色包、新设计场景完成小样，再剪成片。先做相邻两镜，实际检查身份、动作与声音后扩展。看到真实视频并听音；技术解码通过不等于内容通过。 |
| M3：稳定重复制作 | A13–A17 | 连续完成三种不同故事：无对白反应喜剧、短对白反转、接触或照顾；角色身份和声音策略稳定，每片有费用/重做记录，局部修改不触发全片生成。 |
| M4：通用动画模块成立 | A18 | 换成另一组人物、另一套原创场景，使用同一底座完成计划与样片验证。噜噜主题能作为独立包使用。 |
| 后续扩展 | A19–A20 | 基于上述结果决定更多美术、古装动作、额外角色及视频参考控制。 |

第一轮样片优先选单场景、两人、小动作、短对白的故事。厨房/沙发/床边只是当前参考样本，不限制新场景设计。古装火场、多人对战和长合集放在基础闭环之后验证。

## 9. 开发时应完成的测试清单

1. 参考导入：12 个当前样本、中文/emoji/# 路径、重复文件、横竖画布、长短片和合集分段。
2. 剧情依据：OCR 与听音不同来源；不确定说话者保持未知；没有连续观察时不能把完整动作标为已验证。
3. 改编逻辑：必须保留的原因/反应/结果不遗漏；换场景不改变题眼；新剧本中新增内容明确属于原创。
4. 主题复用：噜噜角色包和另一套角色包都可用；换装不改身份，独立短剧之间不继承临时状态。
5. 原创场景：每镜引用新场景版本；不自动取真人原图作动画背景或把来源构图变成硬要求。
6. 生成路由：每次请求不超模型上限，参考数量有验证，未受理/已受理/未知提交走原有不同分支；不能因配套角色包改变原任务归属。
7. 时间映射：参考片时间只作剧情证据；生成秒数、保留秒数、配音和字幕分别准确映射；不得截断关键对白或接触结果。
8. 局部失效：角色图、场景、动作、音色、字幕各自变化只影响依赖产物；旧候选及来源可追溯。
9. 真实小样：分别观察角色辨识、道具接触、表情变化、双人说话、听者反应、跨镜头连续性、声音和题眼是否成立。不能用计划字段或几张静帧代替全片验收。

这些测试属于未来开发清单，本轮未新增实现测试、未运行付费小样。

## 10. 用户后续使用方式

用户发送参考视频，并选择或沿用“噜噜与噜妹”等主题。系统先提炼剧情，然后给出新剧本、新角色/场景设计和分镜；在既有授权与额度内完成试镜、扩展、剪辑和审看。参考角色不明确时再问必要问题，其余创作选择按主题配置推进。

长期目标是形成一个可重复的动画创作流程：故事可以来自真人短视频，也可来自其他视频或文字；人物与场景由所选主题及本片原创设计决定。首轮开发优先把一个短故事做完整，再增加角色包和批量制作。
