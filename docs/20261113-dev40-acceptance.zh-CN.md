## 用户能看到的变化

管理器启动遇到无效 JSON、非 UTF-8 或受支持版本的结构错误时，打开“配置检查与修复”。用户可在本机载入原文、编辑草稿，或选择有效备份作为草稿及身份基准，先预览再保存。初始编辑器不自动显示原文；重新载入会询问放弃有改动的草稿，关闭取消时保留输入，保存事务忙时阻止用户关闭。

预览绑定源文件的原始字节、草稿文本及基准备份。任一变化都需要重新预览；保存先在配置锁内重新核对，再将原始字节保存并校验为 `.raw` 备份，最后原子替换配置。原文的 BOM、CRLF 和无法解码字节都完整保留；备份路径若已存在不同内容则拒绝覆盖。配置已提交后若脱敏历史写入失败，会明确提示，原始备份保留。

成功修复后直接进入正常管理器。有效配置继续使用普通保存/恢复入口；明确不支持的版本保持只读，包括后续语法损坏的较新版本。

CLI 使用同一离线服务：`providers repair-inspect` 返回源字节 token，`repair-preview --file LOCAL_DRAFT --token SOURCE_SHA` 返回修复预览，`repair-apply` 还必须提供 `--preview-token`；可选 `--baseline VALID_BACKUP`。命令、报告、历史均不输出配置原值。

## 身份与证据边界

可解析原文或选定有效备份中的缺失型号、上游、binding 和 route 保留，前三类归档、binding 禁用。已知上游地址和账户不能换到同一个 ID 上；原文与基准备份若对同 ID 的身份有冲突，要求明确核对并使用不同 ID，旧备份不能覆盖后来已知账户。

无法判断的身份单独报告；不能解析的原文不能证明所有历史身份。结构修复不证明密钥可用、旧任务可恢复或上游支持某项操作。修复不修改 DPAPI、项目、任务、账本或媒体证据，也不联网或创建媒体。
